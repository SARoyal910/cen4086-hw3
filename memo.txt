Homework 4 Part 5 Cost Memo

Business: GardenGuru support chatbot

This memo compares two ways GardenGuru could run the chatbot in production: a per-token API model and an always-on rented GPU.

Per-token API assumptions:
Input price: $0.60 per 1,000,000 input tokens
Output price: $2.40 per 1,000,000 output tokens
Average exchange: 900 input tokens and 250 output tokens

Cost per exchange:
900 input tokens x $0.60 / 1,000,000 = $0.00054
250 output tokens x $2.40 / 1,000,000 = $0.00060
Total per exchange = $0.00114

Quiet month: 600 customer questions
Input: 600 x 900 = 540,000 input tokens
Input cost: 540,000 x $0.60 / 1,000,000 = $0.324
Output: 600 x 250 = 150,000 output tokens
Output cost: 150,000 x $2.40 / 1,000,000 = $0.36
Total API cost: $0.684, about $0.68

Busy month: 45,000 customer questions
Input: 45,000 x 900 = 40,500,000 input tokens
Input cost: 40,500,000 x $0.60 / 1,000,000 = $24.30
Output: 45,000 x 250 = 11,250,000 output tokens
Output cost: 11,250,000 x $2.40 / 1,000,000 = $27.00
Total API cost: $51.30

Always-on rented GPU:
GPU price: $0.526 per hour
Monthly runtime: 730 hours
Monthly cost: $0.526 x 730 = $383.98

The rented GPU costs $383.98 for the quiet month and $383.98 for the busy month because it is running all month either way.
The price does not change based on how many customer questions it answers.

Recommendation:
For GardenGuru, the API is better for both the quiet month and the busy month.
At 600 questions, the API costs about $0.68 instead of $383.98. At 45,000 questions, the API costs $51.30 instead of $383.98.

The break-even point is:
$383.98 / $0.00114 per exchange = about 336,825 exchanges per month

Below about 337,000 exchanges per month, the API is cheaper. The rented GPU only starts to make sense for very high, steady usage where the machine will stay busy.
The API model shows the cloud pricing trait of measured service, because GardenGuru pays only for what it uses.
The always-on GPU shows the Week 1 warning about paying for idle resources, because the business pays for the server even when no customers are asking questions.

Classification calls:

1. Chat transcripts
Chat transcripts can contain personal details, so they should be treated as personal information.
If some customers are Canadian, GardenGuru must store and process those transcripts in a way that follows Canadian privacy requirements.
The safest design decision is to keep Canadian customer transcripts in a Canadian or Canadian-compliant storage region and limit who can access them.

2. Payment card numbers
Credit card numbers are highly sensitive payment data covered by PCI-DSS rules. The bot should not look up, store, or display full card numbers to check payment status.
The correct design decision is to keep card data inside a payment processor and let the bot use a safe order ID, payment status token, or last-four-digits reference instead of raw card numbers.


Homework 4 Part 5 Collaboration Memo

Business: GardenGuru support chatbot

Meeting cost:
A weekly 45-minute all-hands for four people costs 4 attendees x $40/hour x 0.75 hours = $120 per meeting. Over 52 weeks, that is $6,240 per year.

Async alternative:
At least half of the agenda should move to a shared document with comments on the one master copy. Policy updates, status notes, customer trends, and routine decisions can be handled there. 
The remaining synchronous time should be for decisions that need live discussion, such as resolving disagreements, choosing between tradeoffs, and assigning ownership.

Tooling choice:
Chat: Google Chat, because it is simple for a small team, uses Google identity, and integrates with Drive and Calendar.

Docs: Google Drive and Google Docs, because they support one shared master copy, comments, permissions, version history, and export to standard formats.

Meetings: Google Meet, because it uses the same identity system and calendar invites without adding another account system.

Selection criteria:
Cost and free-tier edges matter because this is a four-person team and the tools should not cost more than the problem they solve. 
Identity and SSO fit matter because access should follow real users, not shared passwords. Data export matters because GardenGuru should be able to leave the tool later. 
Integration matters because chat, docs, calendar, and meetings should connect cleanly. Permissions matter because private drafts should not become public by accident. 
Ease of use matters because a small team will not maintain a complicated collaboration stack.

Bucket cost:
The site is roughly 1 MB, which is about 0.001 GB. At $0.023 per GB-month, storage costs about $0.000023 per month. 
A busy month with 5 GB transferred out is still inside the first 100 GB free transfer tier, so transfer is $0 in this model. The S3 hosting cost is effectively less than one cent per month, not counting tiny request charges.

Comparison:
Three seats of a $6/user/month collaboration SaaS cost $18 per month. That price is not really buying raw storage, because the storage itself is nearly free. 
It is buying identity, permissions, sharing workflows, comments, notifications, version history, search, support, and an interface normal users can operate without using the AWS console.


Homework 5 Part 5 Design Memo

1. Request classifications

Grounded policy document request: "Can GardenGuru identify a plant from my photo?" This should be answered from the Plant Identification policy because it asks about published app behavior, not a private customer record.

Grounded policy document request: "Will GardenGuru warn me before frost?" This should be answered from the Weather and Frost Alerts policy because the answer is stable business knowledge from the policy documents.

Read tool request: "What is the status of ORD-1002?" This needs get_order_status because the answer depends on the current order store, not a policy document.

Read tool request: "Can you show me ticket TKT-ABCD1234?" This needs get_ticket because the answer depends on an existing saved support record.

Write proposal: "Please open a ticket for ORD-1001 because my shipment has not moved for three days." This proposes changing support data, so create_support_ticket should run only after showing the exact order ID and issue and getting confirmation.

Write proposal: "The package for ORD-1003 arrived damaged; create a case." This also changes support data and may include customer details, so it needs explicit approval before the write.

2. Enforcement layers

Schema validation catches malformed tool input before tool logic runs, such as orderId "1001" instead of the required ORD-0000 pattern. The other layers should not need to guess whether malformed input is usable.

Server business rules catch requests that are well-shaped but unsafe or false, such as ORD-9999 not existing or confirmed being false. A schema can verify format, but only the server can check the actual order store and protect side effects.

Host and human approval catches authorization failures, such as a customer note or model output trying to approve its own write. The host should show the proposed change to the user, and the user must approve it before the server receives confirmed=true.

3. What MCP standardizes

MCP standardizes how a client discovers and calls resources, tools, and prompts, including machine-readable tool schemas and stdio/JSON-RPC communication. It does not supply the model, RAG index, authentication policy, database, or automatic trust. The Inspector ran no model or inference in these tests; it only connected to the MCP server and exercised the published contracts.

4. Pre-approval recommendation

Pre-approve low-consequence read-only access such as reading business://policies and calling get_order_status or get_ticket for records the user is allowed to view. These actions do not change stored data.

Always require a confirmation dialog for create_support_ticket. It changes persistent support records, may include sensitive customer issue text, and can create operational work for staff. The criteria are consequence, reversibility, and data sensitivity, not whether the AI seems confident.
